# Work4ce Assistant

A vendor-neutral security operations platform under active development. The working synthetic investigation slice uses interchangeable REST and MCP connectors, trusted backend policy, evidence-backed reports, and SQLAlchemy persistence. Authentication supports configured demo tokens or an OIDC JWT verifier. Production mode remains disabled.

The [master specification](docs/MASTER_SPECIFICATION.md) is the requested roadmap. [Progress](docs/implementation-progress.md), [known issues](docs/known-issues.md), and [release readiness](docs/release-readiness.md) describe verified delivery.

## Local development

Use Python 3.12 and Node 24 (verified with 24.19.0/npm 11.9.0), and run commands from the repository root:

```sh
./scripts/setup.sh
. .venv/bin/activate
```

Setup checks pinned Python dependencies, builds the Next.js dashboard using `npm ci`, installs the project editable, and runs `pip check`. Matching staged dashboard assets are reused. Network access is needed for missing packages or a fresh dashboard build. `WORK4CE_BUILD_DASHBOARD=0` supports backend-only setup; an unbuilt workbench returns 503.

For a clean environment:

```sh
python -m venv .venv
. .venv/bin/activate
python -m pip install -r requirements.lock
python scripts/build_dashboard.py
python -m pip install --no-build-isolation --no-deps -e .
python -m pip check
```

The lock pins the 42-package Python 3.12/Linux closure, including setuptools 84.0.0 for builds and packaging 26.3 for development verification. It is generated by `scripts/lock_dependencies.py`. Clean installation of all 42 locked distributions in an isolated environment passed `pip check`. The lock has no downloaded-artifact hashes and is not an advisory assessment. Network-permitted commands work; sandboxed commands can report proxy connection errors.

Choose authentication through secure environment configuration:

- Default `WORK4CE_AUTH_MODE=demo`: set distinct random ASCII `WORK4CE_DEMO_TOKEN` and `WORK4CE_ADMIN_TOKEN`, each at least 32 characters. No universal credentials are shipped.
- `WORK4CE_AUTH_MODE=oidc`: configure trusted issuer, dedicated API audience, HTTPS JWKS URL and an explicit server-side subject-role mapping. See [OIDC setup](docs/tutorials/oidc.md). Demo tokens are ignored in this mode.

`WORK4CE_MODE` remains `demo` in either authentication mode. The backend always assigns the `synthetic-demo` tenant. Token claims cannot change tenant or connector permissions.

Start the isolated REST fixture service in one terminal:

```sh
PYTHONPATH=src python -m work4ce_assistant.reference_servers rest --port 8766
```

Start the API in another terminal with its configured authentication:

```sh
PYTHONPATH=src python -m work4ce_assistant serve
```

The MCP connector starts its approved local reference server through the official SDK over stdio. No production vendor credentials are used. The API defaults to port 8765; `WORK4CE_REST_URL` defaults to the approved demo service `http://127.0.0.1:8766`.

`WORK4CE_DB` defaults to `.local/work4ce.db`. SQLite paths and supported SQLite URLs auto-migrate. PostgreSQL requires an explicit migration before API startup; see [database setup](docs/tutorials/database.md). Protect database credentials and files.

```sh
PYTHONPATH=src python -m work4ce_assistant demo investigate --query PowerShell
PYTHONPATH=src python -m unittest discover -s tests -v
```

The CLI uses `WORK4CE_DEMO_TOKEN` in demo authentication mode and `WORK4CE_ACCESS_TOKEN` in OIDC mode. It delegates protected operations to the backend.

## Analyst workbench

The API serves a built Next.js/React/TypeScript dashboard at `/workbench/`. It uses real backend APIs for investigation creation, paginated case history and loaded-case search/filtering, evidence citations, human report decisions, case assignment/escalation, incident resolution and evidence-linked notes, separately approved synthetic dry runs, and connector status. See [the workbench guide](docs/tutorials/workbench.md).

Use an existing configured analyst or reviewer access token. It stays in browser memory and clears on reload/sign-out. OIDC redirect login is not implemented. Use **Load older investigations** to extend the initial 50 cases. Refresh loads the latest page again. Search, status filters and counts cover loaded history; they are not global SOC analytics. All evidence is synthetic; simulations always record `performed:false`.

```sh
python scripts/build_dashboard.py
(cd apps/dashboard && npm run typecheck)
python scripts/test_workbench_browser.py
```

Browser checks require Chromium/Chrome, or `WORK4CE_BROWSER_EXECUTABLE` pointing to a compatible executable. Ten real-browser checks passed, covering analyst/reviewer approval flow, session clearing, literal untrusted markup, mobile layout, paginated history with delayed-response refresh protection, assignment/escalation with stale-edit rejection, the incident lifecycle with concurrent activity loading, multi-investigation linking with source-specific citations, both operational queues beyond 50 records with delayed-page refresh protection, guided onboarding with readiness failures and stale-response fences, and admin source review/disable/re-enable with stale edits and complete-source recovery. The production static build and typecheck passed; npm's production-dependency audit reported zero known vulnerabilities at verification time. This does not establish comprehensive security or accessibility certification.

Open **Getting started** for a [guided first synthetic investigation](docs/tutorials/onboarding.md): validate current database/connector access, inspect the configured reasoning/review policy and launch the existing PowerShell investigation form. Setup checks do not invoke a model or change settings.

## API workflow

Data and control operations require bearer authentication. The static workbench shell is public; its APIs require a token. `/health` checks liveness; authenticated `/ready` probes enabled connectors.

| Operation | Purpose |
|---|---|
| `GET /me` | Read server-assigned identity and permissions |
| `GET /investigations/history?limit=50&cursor=…` | Retrieve a scoped page and an optional next cursor |
| `GET /investigations?limit=50` | List owner-scoped cases; authorized reviewers see their tenant |
| `POST /investigations` with `{"query":"PowerShell","limit":20}` | Collect synthetic events and store a report |
| `GET /investigations/{id}` | Retrieve an authorized report |
| `POST /investigations/{id}/resume` | Manually resume an owner-scoped durable workflow |
| `POST /investigations/{id}/cancel` | Cancel and fence later completion |
| `GET /investigations/{id}/state` | Inspect owner-scoped progress and persisted budgets |
| `GET /capabilities` | Discover registered capabilities |
| `GET /connectors` | Inspect approved connectors |
| `POST /connectors/{id}/disable` | Disable a connector with backend-assigned admin authorization |
| `GET /cases` | List coordinated cases visible to the current actor |
| `GET /case-assignees` | Read eligible server-configured assignees |
| `GET /investigations/{id}/case` | Read assignment and escalation metadata |
| `POST /investigations/{id}/case/assignment` | Assign or unassign with an expected revision |
| `POST /investigations/{id}/case/escalation` | Request management attention with a reason |
| `POST /investigations/{id}/case/acknowledge` | Manager acknowledgment of a pending escalation |
| `POST /incidents` | Create an incident with a primary collected investigation |
| `GET /incidents/{id}/investigations` | Read linked source metadata and evidence choices |
| `POST /incidents/{id}/investigations` | Link a related collected investigation with a revision and reason |
| `GET /incidents` | List incidents in current case scope |
| `GET /incidents/{id}/activity` | Read authored notes and status history |
| `POST /incidents/{id}/notes` | Append a note with optional source evidence references |
| `POST /incidents/{id}/status` | Change status with revision and manager checks |
| `GET /health` | Check API liveness |
| `GET /ready` | Probe enabled connectors |

Use `Idempotency-Key` to bind retries to the same tenant/subject request. Add `"defer":true` to queue a request with `202`, then explicitly resume it; no automatic worker is started. See [durable workflows](docs/tutorials/workflows.md) for checkpoints, leases, cancellation and persisted budgets.

Inspect evidence provenance, disable the selected connector as an admin, and repeat the same investigation to observe authorized replacement. Connector failure remains explicit. Disablement and guarded re-enable reviews persist. Administrators can use [reviewed connector controls](docs/tutorials/connector-controls.md); re-enabling requires current revision/hash, fresh discovery and a healthy source.

## Verification and scope

The complete suite passed **431 tests in 129.209 seconds with zero skips** against real PostgreSQL 17.11 and SQLite. The suite exercises real REST/MCP replacement, persisted budgets and cancellation, migration/queue concurrency, and RSA-signed JWT verification against mocked HTTPS JWKS. Four end-to-end tests terminate a real worker after checkpoint commit, restart the API, and verify stable evidence without another REST search on both databases. No live identity provider was verified. The current wheel serves dashboard HTML and seven JavaScript assets with CSP; authenticated identity, scoped history, case coordination, multi-investigation incidents, two-page operational queues, onboarding status, reviewed connector controls and migration 0008 passed from an isolated installed wheel. Human review/dry-run installed-wheel validation passed in an earlier increment. All 42 dependency pins and `pip check` passed.

Trusted workflow defaults are configured through `WORK4CE_MAX_TOOL_CALLS` (2; range 1–8) and `WORK4CE_INVESTIGATION_TIMEOUT_SECONDS` (120 seconds; range 0.01–600). Request bodies cannot override these limits.

For isolated PostgreSQL integration testing, run `python scripts/test_postgres.py` with Docker available. The runner creates and removes only its own temporary PostgreSQL container/data. The Compose file provisions a development database, not an application deployment.

The default investigator remains deterministic. Optional structured assistance supports an offline fixture and a configured HTTPS model adapter; see [model setup](docs/tutorials/models.md). Plans cannot enlarge query scope, and observations require exact evidence quotations. No live LLM or AI accuracy claim is made. Production OIDC operations, database TLS/RLS, automatic workflow scheduling, broader AI planning, live response execution, full SOC dashboard coverage and live security integrations remain incomplete. See [specification status](docs/prompt-status.md), [architecture](docs/architecture/decisions.md), [threat model](docs/security/threat-model.md), and [next steps](docs/next-steps.md).

Structured model assistance is selected by the trusted `WORK4CE_REASONING_MODE` setting (`deterministic`, `fixture`, or explicitly configured `provider`). Model request/cost reservations and validated results persist through migration `0003_models`. Provider mode requires a credential, explicit pricing and synthetic-egress opt-in; no live provider is configured by default. See [the model gateway guide](docs/tutorials/models.md).


Human review and synthetic action approvals are now available through [the review workflow](docs/tutorials/reviews.md). `WORK4CE_REQUIRE_HUMAN_REVIEW=true` gates report acceptance after collection; the default remains false for compatibility. Action proposals always require an approved report review and a separate approval from another actor. Simulation consumes a matching unexpired approval exactly once and records `dry_run:true, performed:false`; no external response is executed. Server-mapped OIDC `reviewer` is supported without investigation or simulation execution grants.

Case assignment and escalation are available through [case coordination](docs/tutorials/cases.md). Eligible assignees come from trusted server configuration. Creators/current assignees coordinate their cases; managers can coordinate any case and acknowledge escalations. Reviewers have read access. These edits preserve the original workflow requester, report contents and independent approval gates. PostgreSQL requires migration `0008_connector_controls` before starting the updated API; SQLite upgrades automatically.

[Incident management](docs/tutorials/incidents.md) now supports human-entered title/severity, work status, resolution, manager closing/reopening, and append-only notes with evidence references. Each incident keeps a primary investigation and supports up to nine related sources. Viewing or editing it requires current case access to every linked source. Incident disposition is separate from report acceptance and response approvals. Activity is bounded to 200 entries; unlinking/merging, SLAs and notifications remain future work. [Operational queues](docs/tutorials/queues.md) now load older pages explicitly in creation order, with current access checked on every request.

Linking adds a source-hash binding and an authored activity entry. A combined incident can have a narrower audience than its individual cases: reassignment of any source can revoke access to the entire incident. Notes use investigation-qualified evidence references; legacy `evidence_ids` still cite the primary source. All-source pending escalations block resolution/closing.
