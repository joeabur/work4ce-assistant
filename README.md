# Work4ce Assistant

A vendor-neutral security operations platform under active development. The working synthetic investigation slice uses interchangeable REST and MCP connectors, trusted backend policy, evidence-backed reports, and SQLAlchemy persistence. Authentication supports configured demo tokens or an OIDC JWT verifier. Production mode remains disabled.

The [master specification](docs/MASTER_SPECIFICATION.md) is the requested roadmap. [Progress](docs/implementation-progress.md), [known issues](docs/known-issues.md), and [release readiness](docs/release-readiness.md) describe verified delivery.

## Local development

Use Python 3.12 and run commands from the repository root:

```sh
./scripts/setup.sh
. .venv/bin/activate
```

Setup reuses the prepared runtime, checks pinned dependency versions, installs missing or mismatched locked packages when needed, installs the project editable, and runs `pip check`. It can run offline when the pinned dependencies already exist. Network access is needed when packages must be installed.

For a clean environment:

```sh
python -m venv .venv
. .venv/bin/activate
python -m pip install -r requirements.lock
python -m pip install --no-build-isolation --no-deps -e .
python -m pip check
```

The lock pins the 40-package Python 3.12/Linux closure, including setuptools 84.0.0 for builds and packaging 26.3 for development verification. It is generated by `scripts/lock_dependencies.py`. Clean installation of all 40 locked distributions in an isolated environment passed `pip check`. The lock has no downloaded-artifact hashes and is not an advisory assessment. Network-permitted commands work; sandboxed commands can report proxy connection errors.

Choose authentication through secure environment configuration:

- Default `WORK4CE_AUTH_MODE=demo`: set distinct random ASCII `WORK4CE_DEMO_TOKEN` and `WORK4CE_ADMIN_TOKEN`, each at least 32 characters. No universal credentials are shipped.
- `WORK4CE_AUTH_MODE=oidc`: configure trusted issuer, dedicated API audience, HTTPS JWKS URL and an explicit server-side subject-role mapping. See [OIDC setup](docs/tutorials/oidc.md). Demo tokens are ignored in this mode.

`WORK4CE_MODE` remains `demo` in either authentication mode. The backend always assigns the `synthetic-demo` tenant. Token claims cannot change tenant or connector permissions.

Start the isolated REST fixture service in one terminal:

```sh
PYTHONPATH=src python -m work4ce_assistant.reference_servers rest --port 8766
```

Start the API in another terminal with its configured authentication:

```sh
PYTHONPATH=src python -m work4ce_assistant serve
```

The MCP connector starts its approved local reference server through the official SDK over stdio. No production vendor credentials are used. The API defaults to port 8765; `WORK4CE_REST_URL` defaults to the approved demo service `http://127.0.0.1:8766`.

`WORK4CE_DB` defaults to `.local/work4ce.db`. SQLite paths and supported SQLite URLs auto-migrate. PostgreSQL requires an explicit migration before API startup; see [database setup](docs/tutorials/database.md). Protect database credentials and files.

```sh
PYTHONPATH=src python -m work4ce_assistant demo investigate --query PowerShell
PYTHONPATH=src python -m unittest discover -s tests -v
```

The CLI uses `WORK4CE_DEMO_TOKEN` in demo authentication mode and `WORK4CE_ACCESS_TOKEN` in OIDC mode. It delegates protected operations to the backend.

## API workflow

All operations except `/health` require bearer authentication. `/health` checks liveness; authenticated `/ready` probes enabled connectors.

| Operation | Purpose |
|---|---|
| `POST /investigations` with `{"query":"PowerShell","limit":20}` | Collect synthetic events and store a report |
| `GET /investigations/{id}` | Retrieve an authorized report |
| `POST /investigations/{id}/resume` | Manually resume an owner-scoped durable workflow |
| `POST /investigations/{id}/cancel` | Cancel and fence later completion |
| `GET /investigations/{id}/state` | Inspect owner-scoped progress and persisted budgets |
| `GET /capabilities` | Discover registered capabilities |
| `GET /connectors` | Inspect approved connectors |
| `POST /connectors/{id}/disable` | Disable a connector with backend-assigned admin authorization |
| `GET /health` | Check API liveness |
| `GET /ready` | Probe enabled connectors |

Use `Idempotency-Key` to bind retries to the same tenant/subject request. Add `"defer":true` to queue a request with `202`, then explicitly resume it; no automatic worker is started. See [durable workflows](docs/tutorials/workflows.md) for checkpoints, leases, cancellation and persisted budgets.

Inspect evidence provenance, disable the selected connector as an admin, and repeat the same investigation to observe authorized replacement. Connector failure remains explicit. Disablement persists; no enable/review API exists.

## Verification and scope

The complete suite passed **120 tests in 39.650 seconds with zero skips** against real PostgreSQL 17.11 and SQLite. The suite exercises real REST/MCP replacement, persisted budgets and cancellation, migration/queue concurrency, and RSA-signed JWT verification against mocked HTTPS JWKS. Two end-to-end tests terminate a real worker after checkpoint commit, restart the API, and verify stable evidence without another REST search on both databases. No live identity provider was verified. The current wheel was rebuilt and isolated installed-wheel migration 0002 and workflow completion passed. All 40 dependency pins and `pip check` passed.

Trusted workflow defaults are configured through `WORK4CE_MAX_TOOL_CALLS` (2; range 1–8) and `WORK4CE_INVESTIGATION_TIMEOUT_SECONDS` (120 seconds; range 0.01–600). Request bodies cannot override these limits.

For isolated PostgreSQL integration testing, run `python scripts/test_postgres.py` with Docker available. The runner creates and removes only its own temporary PostgreSQL container/data. The Compose file provisions a development database, not an application deployment.

The investigator is deterministic; no LLM or AI accuracy claims are made. Production OIDC operations, database TLS/RLS, automatic workflow scheduling, AI planning, response approvals, dashboard and live security integrations remain incomplete.
