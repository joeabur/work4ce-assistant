# Known issues and limitations

- Initial sandbox proxy errors did not establish network failure. Network-permitted Git checks succeeded; Python dependency advisories and official stable-version status remain unreviewed.
- Production mode remains disabled even with OIDC. Signed-token verification and backend role mapping are tested against fixtures, not a live provider. Browser login, account administration, enterprise identity lifecycle and deployed TLS remain pending.
- SQLite and PostgreSQL use SQLAlchemy with Alembic migrations. PostgreSQL 17.11 integration passed, but production TLS, least-privilege migration/runtime separation, database RLS, encryption, backup/restore and operational recovery remain incomplete.
- Persistence is synchronous and can block the API event loop. Engine pools are bounded to four connections; this does not establish scalable concurrency. Auth request rates, terminal workflow retention and audit retention are unbounded. Nonterminal queue admission is capped at 100 per tenant/subject.
- Reports and connector disablement survive restart. Durable workflows now support explicit manual resume with checkpoints, scoped idempotency and lease-fenced cancellation; there is no automatic scheduler. An interrupted read without a committed checkpoint may repeat within its persisted budget. Remote I/O already in flight may continue after cancellation, but cannot overwrite cancellation. General multi-step recovery remains incomplete.
- The default and offline fixture remain deterministic. A typed model gateway and configured HTTPS adapter are implemented and fixture-tested. No live LLM, broader threat-reasoning accuracy, LangGraph runtime or independent AI evaluation is verified. Input pattern blocking is limited, provider usage/prices are unverified billing, and inference interrupted before cache commit may repeat within the reserved budget.
- MCP support targets one approved local stdio server through the official SDK. Remote MCP OAuth and general interoperability are unverified. Reference security telemetry is synthetic; no live SIEM/EDR/cloud integration is verified.
- JWT `JWT` and `at+jwt` header types are supported. Configure a dedicated API audience to avoid browser ID-token substitution. Valid cached JWKS keys may remain usable for up to 300 seconds after provider removal; broader revocation policy is absent.
- Report review and single-use approvals are tested for synthetic simulation only. Production response execution, a privileged isolated worker, complete CDK packaging, broad SOC dashboard modules, operational monitoring and application deployment validation remain pending. Pending report review has no separate backlog quota; response proposals are capped at 100 pending/approved per requester, including expired proposals until revocation. Approved report-review retraction is not implemented.
- Audit records are stored locally or in the configured database without a tamper-resistant remote trust boundary. Hashes do not prove source truth or protect against a privileged database writer.
- No connector enable/review administration API exists. Built-ins are approved by trusted bootstrap; existing disablement persists. New connector enablement requires reviewed backend configuration.
- The 42-package dependency lock pins Python 3.12/Linux versions without downloaded-artifact hashes. Clean installation of all 42 distributions and `pip check` passed; wheel build and isolated installed-wheel persistence/migrations also passed. This is not a security/advisory scan.
- The Compose service provisions only a development database. Its Compose startup is unrun; the isolated test runner did start the pinned database image successfully. Remote GitHub CI remains unverified after a native status query returned Forbidden; production application deployment has not executed.
- No repository license is assumed. The owner should choose licensing before external distribution.

Record exact final verification counts and unrun checks in `release-readiness.md`.

- The workbench supports investigations, evidence, reviews, synthetic approvals and connector status. Case history loads 50 entries per page (API maximum 100), with explicit loading of older pages. Search and counts apply to loaded history; refresh resets to the latest page. Broader incident operations, general SOC analytics, connector administration and first-run onboarding are pending. OIDC redirect login is absent; use an already-issued API token, held only in memory. Signing out does not revoke the server token.
- Building the dashboard requires Node/npm and the npm registry/cache. Backend-only installs can omit generated assets, in which case `/workbench/` returns 503. Build before producing a distributable wheel. Chromium/Chrome is needed for the separate browser runner. Desktop/mobile rendering and workflow were checked, but formal accessibility and cross-browser validation are unrun.
- npm's production-dependency audit returned zero known vulnerabilities at verification time. Python advisory scans and broader supply-chain/security assessments remain incomplete.

- History cursors preserve position, not a database snapshot. Newer investigations appear after refresh; statuses can change between pages. Review and response queues still use their existing bounded lists. Large-history query performance and load testing remain unverified.

- Case coordination supports assignment, unassignment, escalation/re-escalation and manager acknowledgment. Its list loads at most 50 rows by default (API maximum 100) without UI pagination. One current escalation reason is retained; the audit records actors/actions/revisions rather than a full content history. Case reasons remain a current-value field; linked incident activity separately retains notes and status history. SLA routing and external notifications/directory synchronization remain incomplete. Assignment preserves the immutable workflow requester and existing approval rules.

- Incidents bind a primary and at most nine related collected investigations. The queue is bounded to 50 by default (API max100) without UI pagination. Activity is append-only through the API and capped at 200 entries including creation/status changes; closed incidents require manager reopening before more notes. Standalone incidents, unlink/merge governance, title/severity editing, SLAs and notifications remain incomplete. Database administrators can alter stored history; no tamper-resistant storage boundary is claimed. Incident resolution preserves independent report and response gates.

- Combined incident access requires current visibility of every linked case, so linking or reassignment can narrow its audience. Sources are immutable members after linking in this slice. Queue filtering enforces all-source scope before the limit, but validating selected groups performs bounded per-source reads; large groups/queues and remote-database latency remain unbenchmarked.
